The server relays your meeting. It cannot hear it.

NME is a small, fast group video app. Audio, video, and messages are encrypted on your device and decrypted only on the devices of the people you invited. Nothing in between holds the key — including the server you are running it on.

Everything after the # is a URL fragment, and browsers do not transmit fragments in HTTP requests. That is where the encryption key lives. The server issues the room and the join token, and has no way to learn the key — so holding the link grants access, and holding the server does not.

How it works

Two layers of encryption, one of which the server is outside of

Ordinary WebRTC encrypts each hop. Media is protected on the wire, but the routing server decrypts it, looks at it, and encrypts it again — which is how nearly every meeting product works, and why nearly every one of them can record you.

NME adds a second layer underneath. Frames are encrypted with AES-GCM before they are handed to WebRTC at all, so the SFU forwards ciphertext it has no key for. It can still do its job — deciding who needs which quality — because selecting between encrypted layers never requires reading them.

DTLS-SRTP

Standard WebRTC transport encryption. Protects each hop. The server terminates it.

AES-GCM frame encryption

Applied in your browser or on your phone, before the media ever reaches the network. The server never holds this key.

No accounts

No sign-up, no directory, no profile. A meeting is a link. That is the whole model.

Nothing stored

No recordings, no transcripts, no chat history. Messages live in memory and are gone when the tab closes.

Safety number

A short fingerprint of the room key. Read it aloud to confirm two people opened the same invitation.

Ask to join

A lobby, so someone already in the meeting decides who comes in — and that authority disappears when they leave.

Works on locked-down networks

If a firewall blocks direct media, the call falls back to a TLS relay on port 443. The relay carries ciphertext too.

iOS and Android

Native apps using the platform frame cryptor, not a web view. Meeting links open straight into them.

Honestly

What this protects, and what it does not

Security writing tends to list only the wins. These are the limits, in plain terms, because a tool you misjudge is more dangerous than one you understand.

  • ✔Content is unreadable by the server. Audio, video, screen share, and chat are encrypted before they leave your device.
  • ✔A seized or subpoenaed server yields ciphertext. There is no key on it to hand over, and nothing recorded to seize.
  • ✔No downgrade path. If a browser cannot encrypt end to end, NME refuses to connect rather than quietly joining in the clear.
  • ✘Metadata is visible. The server sees that a meeting exists, when, for how long, and how much bandwidth each participant used.
  • ✘Anyone with the link can join. The link is the secret. Send it the way you would send a password.
  • ✘Participants can record. Everyone in a call necessarily holds decrypted media. No software can prevent a screen recorder, let alone a second phone pointed at the screen.

Self-host

Your server, your rules

One Docker Compose stack: a Fastify control plane, a LiveKit SFU, Redis, and Caddy for TLS. Runs comfortably on a small VPS. 

# Clone, generate secrets, run.
git clone https://github.com/aneeshtan/NME.git
cd NME
npm run keys        # writes .env

docker compose -f infra/docker-compose.yml \
  --env-file .env up -d --build

Caddy obtains and renews certificates automatically. Point a domain at the box and it is live.

The control plane is stateless and out of the media path, so restarting or redeploying it does not drop anyone already in a call. Media never passes through the reverse proxy.
